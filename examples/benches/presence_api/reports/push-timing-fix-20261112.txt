Root cause: historical RPC binding used against the deployed push protocol.

Cursor f6559e87 used method 35 + uint32 request ID + UID, and awaited result 0.
The client streaming main had migrated registration and Ping to the deployed
push protocol, but the presence port retained this historical RPC declaration.

The published io.aether:client-server-work-api:0.0.100 and 0.0.101 artifacts
define method 35 as void getClientTiming(UUID uid). Its 17-byte request has no
request ID. ClientApiSafe.sendClientTiming is method 41, carrying UID followed
by lastActivityDeltaMs and nextPingDeltaMs (33 bytes, signed 64-bit timings).
Generated Java and ADSL agree. The source jars are byte-identical with SHA256
007ad6b2a855f1720ae3cb95146dec2077792484a9d4d17dd2da2b7ef084ccff.
See published-timing-contract-provenance.json for URLs and hashes.

The four extra RPC bytes became the beginning of the target UID. The receiver
also lacked push method 41. Missing next-Ping announcements cannot explain
this failure: the client was sending the wrong UID and waiting on another
response mechanism. Earlier reports of no method-35 RPC replies are historical
observations of this broken port, not evidence that the server lacks presence.

Fix: void method-35 binding; typed method-41 dispatch; subscribe before writing;
match UID on the resolved server connection; unsubscribe on completion/destruction.
Retries retain the first send-time anchor on a connection. No server changes,
dependency changes, global network/firewall operations, or remote commits.

Protocol limitation: the push includes UID but no request sequence. It cannot
prove per-attempt freshness across a timed-out query and a replacement query.
This limitation is separate from the fixed wire-format and dispatch bugs.

Regression tests use literal published-wire byte fixtures, not an SDK-generated
round trip. Additional cases cover foreign UID, duplicate, missing announcement,
synchronous reply during Write, destruction, and timeout without Restream.

Live pilot: both clients confirm 1-second Ping interval/window on servers
20/21/24, then successfully query own UID and peer through the actual API.
20-second healthy baseline: no Unknown or false Offline. Two 3-second scoped
TCP blackouts: both local and peer Offline/Online observed, both recovered.
Maximum local Offline 1951.674 ms, Online 60.923 ms; peer Offline 2051.111 ms,
Online 1398.942 ms. These are two observations, not production percentiles.

Full CTest: 57/57 pass. A/B and cloud smoke tests each pass fresh and saved
state, with seven seconds between fresh/saved runs. Evidence is produced by
the native API benchmark with a private per-process TCP proxy; no echo channel.

The first 8-cut matrix after the wire fix (before the separate Ping lifecycle
correction) completed with two failed stable recoveries: B/10s and B/30s.
All Offline transitions were detected. Maximum successful terminal-stable peer
recovery was 22355.733 ms, only 6/8 recovered stably. Initial Online alone hid
the failure: A/30s was Online after 384 ms, then Offline again 11-21 seconds
after restore because one server's Ping announcement stopped advancing.
SID20,21,24 each appeared in a stalled case; timing DTOs continued to arrive.
The 60-second healthy baseline had 120 peer Online results, no Unknown or false
Offline. These failures therefore concern re-announcement after recovery,
not the now-correct method-35/41 transport.

The separate lifecycle defect: late-Ping handling queued cloud reconciliation
before queuing guarded Ping retirement. Reconciliation may replace the client
connection, so the retirement guard then rejects the old binding and periodic
Ping never resumes. The fix performs recovery/reconciliation scheduling inside
the guarded finish callback, before clearing Ping and scheduling the next run.
Already-recovered nonquarantined connections also retire the late Ping normally.
No speculative receive-window refresh or extra Ping overlap is included.

A subsequent trace reproduced an independent normal-Ok scheduling failure,
even before injecting a fault. One server completed 62 Pings successfully,
then its final Ok cleanup had neither a periodic-task handle nor a deferred
start flag. Other servers continued; the peer's published deadline expired.
The old cleanup only rearmed when the deferred flag was set. Moving all arming
to terminal cleanup was tried and did not solve the underlying disappearance.
The final code retains the original periodic cadence, resets the executing
handle on Start, and ensures a start remains after normal retirement.

The underlying scheduler handoff race was reproduced deterministically:
an IO producer publishes a raw task pointer, the main thread executes/frees it
and reuses its slot for a Ping timer, then the delayed producer attaches its
subscription to the stale address. Cancellation then cancels the unrelated
timer. The broken reproducer observed periodic_calls=0 with overflow=0.
Owned posting attaches/replaces the subscription under the scheduler lock,
before a consumer can reclaim the task. Synchronized cancellation and atomic
active state cover cancellation versus execution. TCP/UDP state and send-result
posts and packet-queue coalescing use this API. The fixed reproducer observed
periodic_calls=1; concurrent owned-post and independent-timer tests also pass.

No unconditional second Ping is sent over an outstanding unnumbered Ack.
Lost replies still follow the bounded soft-quarantine/connection-recreation
path, covered by the missing-Pong expiry regression. A Ping sequence in the
server protocol remains future work; no server change is included here.

Final interim-client validation (code commit 7d02e7ea, on main 3ac320a0):
TCP-only owned-post-matrix, 120-second baseline, 1-second Ping/window/query,
1-second presence tolerance. A and B each blacked out for 3, 10, and 60 seconds.
All 6 outages detected locally and remotely, all 6 recovered stably, no censored
recoveries, no worker restarts. Baseline remained entirely Online on both APIs,
with zero Unknown and false Offline. Recovery was required to remain healthy
for 5 seconds; terminal-stable results equal the first Online results here.
